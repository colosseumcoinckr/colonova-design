# MVP 범위와 안정화 계획

2026-10-20 결정. 출처: 사용자의 최소 기능 보장 후 확장 요청과 후속 작업 지시.
이 문서는 MVP의 지원 범위, 합격 기준, 구현 순서와 검증 상태를 기록한다. 보관·제출 분리와 피드백 자동 실행 축소를 구현했다. 설치본·양쪽 OS·비개발자 베타까지 완료한 상태는 아니다. 현재 동작은 [사용 설명서](GUIDE.md), 구현 상세는 [개발자 안내](DEVELOPERS.md)를 따른다.

## 제품이 보장할 한 바퀴

> 개발자가 준비한 프로젝트에서 비개발자가 화면을 수정하고, 직접 확인하고, 되돌릴 수 있으며, 확인한 변경을 개발자에게 제출할 수 있다.

연결 → 요청 → 화면 확인 → 보관·되돌리기 → 제출 → 추가 수정·재제출 → 개발자 반영 확인 → 다음 작업.

보장 대상은 작업 보존, 상태의 정확성, 제출 내용의 일치, 실패 후 복구다. AI가 모든 요청을 원하는 품질로 완성한다고 약속하지 않는다. 결과의 적합성은 실제 화면과 연결 레포의 검사로 확인한다.

## 지원 조건과 기능 동결

| 항목 | MVP 범위 |
| --- | --- |
| 사용자 | 개발자가 초대 파일과 프로젝트를 준비한 팀의 비개발자 |
| 실행 환경 | 현재 지원하는 macOS Apple 실리콘과 Windows x64. 둘 다 설치본으로 검증한다. 설치 조건은 [설치 안내](../README.md#-시작하기--세-걸음)를 따른다. |
| AI | Claude Code 단일 실행 경로. 개발 규칙과 검사 도구는 연결 레포가 제공한다. |
| 프로젝트 | 설치·실행·검사 명령과 확인할 화면을 개발자가 점검한 연결 레포. 출시 후보마다 레포의 기준 커밋과 시나리오를 기록한다. |
| 작업 단위 | 프로젝트 전체 변경을 한 제출 범위로 다룬다. 다른 대화의 변경도 포함한다. 프로젝트별 AI 수정은 순차 실행한다. |
| 유지할 편의 기능 | 기존 첨부·기본 찍기·크기 전환·프로젝트 전환 등은 유지하되 확장하지 않는다. 노출된 기능의 작업 유실·프로젝트 혼선·핵심 흐름 방해는 출시를 막는다. |

이번 안정화 주기에는 아래 합격 기준을 막는 수정만 한다. 새 공급자, 고급 사진 비교, 여러 프로젝트의 자동 작업 확대는 후속 버전으로 미룬다. 기존 기록 읽기, 보관·복구, git 쓰기 차선과 가드는 유지한다. 프로토콜 버전은 올리지 않는다.

## 필수 합격 기준

아래는 출시 조건이며 현재 통과 결과가 아니다.

| ID | 기능 | 합격 기준 |
| --- | --- | --- |
| M1 | 설치·연결 | 새 사용자 환경에서 설치, AI 로그인, 초대 파일 연결, 첫 화면까지 도달한다. 실패한 단계와 다시 진행할 방법을 표시한다. |
| M2 | 요청·중단 | 요청, 진행, 중단, 실패를 구분한다. 실패나 미검사를 성공으로 표시하지 않는다. 중단 후 같은 프로젝트에서 다시 요청할 수 있다. |
| M3 | 미리보기·찍기 | 현재 프로젝트의 실제 화면이 열린다. 기본 찍기로 위치를 지정해 수정할 수 있다. 서버 실패나 프로젝트 전환 뒤 다른 화면을 현재 결과로 표시하지 않는다. |
| M4 | 보관·복구 | 보관 완료된 파일과 기록이 앱 재시작 후 유지된다. 이전 보관 시점으로 되돌리고 그 되돌림도 복원할 수 있다. 중단 시 디스크에 남은 미보관 변경은 조용히 버리거나 제출하지 않는다. 아직 디스크에 쓰이지 않은 AI 출력까지 복원을 약속하지 않는다. |
| M5 | 제출·재제출 | 확인 창의 프로젝트 전체 최종 변경과 실제 PR 변경이 일치한다. 제출 의도를 확정하기 전에 HEAD·기준 브랜치·작업 내용이 바뀌면 재확인을 요구한다. 재시도와 재시작으로 PR이 중복 생성되지 않는다. 열린 PR에도 새 사용자 변경은 다시 제출한 뒤 전달한다. |
| M6 | 제출 이후 | 코멘트·검사 결과·닫힘·병합을 실제 원격 상태와 맞게 표시한다. 읽지 못함을 성공으로 표시하지 않는다. 병합 뒤 다음 작업과 닫힌 요청 이후의 재제출에서도 기존 작업이 보존된다. 개발자 반영과 서비스 배포는 구분한다. |

베이스 브랜치 직접 쓰기, 작업 유실, 다른 프로젝트로의 제출, 미확인 변경 전송, 중복 PR, 실패를 성공으로 표시하는 문제는 출시 중단 사유다. 자동 복구가 해결하지 못한 충돌은 기존 변경을 보존하고 담당자에게 이어갈 수 있어야 한다. 모든 충돌의 무인 해결은 합격 조건이 아니다.

제출 확정은 버튼 요청을 git 차선 안에서 검증하고 확인한 버전·기준을 제출 의도에 기록한 시점이다. 이후 생긴 새 사용자 변경은 그 제출에서 제외하고, 재시작해도 확정한 버전만 전송한다. 원격 기준이나 PR head가 달라져 확인한 diff를 유지할 수 없으면 재확인을 요구한다. 기존 원장에 확정 버전이 없을 때도 최신 HEAD로 추측해 보내지 않고 재확인한다.

## 제출 이후 자동화의 경계

MVP에서는 코멘트와 검사 결과를 확인하고 사용자가 수정 요청을 보낸 뒤 다시 제출한다. 다음 표의 자동 실행은 후속 버전으로 미룬다. P2에서 자동 실행 판정을 제거하고 사용자 안내를 함께 바꿨다.

| 유지 | 후속 버전으로 미룰 실행 |
| --- | --- |
| 개발자 코멘트와 닫힘 이유의 조회·표시 | 의견·반려를 계기로 AI가 자동 수정하고 재제출·답장하는 작업 |
| CI 결과 조회와 원격 요청 링크 | CI 실패를 계기로 AI가 반복 수정하는 작업 |
| AI 리뷰 의견의 원격 조회 경로 | AI 리뷰를 평가해 자동 수정하는 작업 |
| 요청 상태 관찰, 보관·복구, 사용자가 시작한 제출의 재시도 | 다른 프로젝트에서 피드백 때문에 새 AI 수정 작업을 자동 시작하는 기능 확대 |

감독자 전체를 끄지 않는다. 상태 관찰, 재시도, 보관, 병합·닫힘 후 작업 보존은 핵심 흐름이다. 충돌 복구가 만든 새 변경도 미확인 상태로 기존 PR에 보내지 않도록 P1의 제출 경계를 적용한다.

## 이번 구현

2026-10-20 사용자 구현·검증 요청. [mvp-flow.test.ts](../packages/daemon/test/mvp-flow.test.ts)는 실제 임시 git 원격과 메모리 GitHub를 대조한다. 실제 계정·설치본의 검증과는 구분한다.

- 보관과 되돌리기는 로컬 커밋에서 끝낸다. 제출 의도는 확인한 커밋·기준·화면 기록을 보존한다. 중복 제출·새 보관·재시작으로 확정 버전을 바꾸지 않는다.
- 전송 전에 실제 원격 기준과 head를 확인한다. 확인한 SHA만 전송하고, fast-forward 확인과 lease로 같은 원격 브랜치의 동시 변경을 막는다. 확정 버전이 없는 옛 제출 의도는 재확인을 요구한다.
- 개발자 코멘트·반려·CI·AI 리뷰의 자동 수정 판정을 제거했다. 도착 알림·결과 조회는 유지한다. 시작 복구에서도 옛 `review`·`ci` 턴을 실행하지 않고 기다리던 사용자 요청을 복구 목록에 남긴다.
- 코멘트 카드·검사 줄은 수정을 요청하는 방법을 안내한다. 기록의 시각이나 병합만으로 의견을 반영했다고 추정하지 않는다. 같은 프로젝트에서 요청이 바뀐 뒤 도착한 낡은 코멘트 조회 결과도 표시하지 않는다.
- 설치형 macOS 앱에서 발견한 경로 별칭 판정을 고쳤다. 같은 파일의 `/tmp`·`/private/tmp` 표기 차이로 턴 종료 시 자동 보관이 누락되지 않게 실제 위치를 비교한다. 삭제한 파일도 양방향 별칭 회귀 시험에 포함한다.

## 검증 방법과 증거

코드 변경 뒤 `pnpm typecheck`, `pnpm test`와 CI의 biome 검사를 통과한다. `pnpm test`는 빌드를 포함하며 시험은 `dist`를 읽으므로, 소스만 바꾼 뒤 이전 빌드를 시험하지 않는다. 설치본은 [패키징 절차](DEVELOPERS.md#데스크톱-패키징)로 별도 검증한다. `pnpm dev:desktop` 확인은 설치본 검증을 대신하지 않는다.

검증용 연결 레포와 자격 증명을 사용한다. 실패는 검증 환경에만 주입한다. 예상 화면·파일·PR 결과는 실행 전에 담당 개발자가 정하고, 앱의 성공 문구나 AI의 완료 답변만으로 판정하지 않는다.

| ID | 시나리오 | 독립 확인과 합격 기준 |
| --- | --- | --- |
| N1 | 새 사용자 설치 → 로그인 → 연결 → 수정 → 실제 화면·찍기 확인 → 보관 → 되돌리기와 복원 → 제출 | 미리보기의 실제 조작 결과, 보관된 파일 내용, PR의 base/head와 diff를 대조해 M1–M5를 확인한다. |
| N2 | 다른 대화에서 추가 수정 → 원격 확인 → 재제출 → 별도 개발자 계정 코멘트 → 사용자 수정·재제출 → 병합 → 앱 재시작 → 다음 작업. 별도 사이클에서는 PR 닫힘 → 수정·새 요청 제출도 확인 | 재제출 전 PR head가 유지되고 제출 후 같은 PR이 갱신된다. 코멘트만으로 수정이 시작되지 않는다. 실제 닫힘·병합 상태와 앱 표시가 같다. 병합 후 새 PR에는 이후 변경만 포함한다. 미병합 닫힘 후 새 PR에는 보존한 기존 변경과 추가 변경을 확인한 범위대로 포함한다. |
| F1 | 파일 변경 중 AI 중단, 별도 실행에서 앱 강제 종료 | 종료 전 보관 파일·기록과 디스크에 쓰인 미보관 파일을 재시작 후 대조한다. 새 요청을 진행할 수 있고 미보관 변경이 임의 제출되지 않는다. |
| F2 | 보관 완료 직후·제출 처리 중 앱 종료 후 재시작 | 실제 로컬 커밋과 원격 PR을 대조한다. 확인한 제출은 복구되고 PR은 하나이며 더 최신의 미확인 보관은 전달되지 않는다. |
| F3 | 제출 전 네트워크 단절, 서버에 PR이 생성됐으나 응답을 못 받은 경우, 복구 후 재시도 | 실제 원격 조회로 PR 수와 head를 확인한다. 중복 PR·변경 유실·미확인 버전 전송이 없다. 응답 유실 사례는 자동 시험의 오류 주입과 설치본의 복구 관찰을 구분해 기록한다. |
| F4 | AI 인증 만료와 GitHub 연결 코드 만료·권한 부족을 각각 주입 | 실패한 연결을 구분한다. 새 로그인·연결 복구 후 기존 작업에서 이어간다. 인증 자료를 로그나 증거에 남기지 않는다. |
| F5 | 미리보기 서버 종료·다시 시작, 두 프로젝트를 번갈아 열기 | 현재 프로젝트의 실제 URL·응답·화면을 대조한다. 오래된 화면을 성공 결과로 표시하지 않고, 요청·대화·제출이 다른 프로젝트로 섞이지 않는다. |
| F6 | 제출 확인을 연 뒤 기준 브랜치 변경, 로컬 추가 수정, 충돌 발생 | 낡은 확인으로는 제출되지 않는다. 충돌 시 양쪽 변경이 보존되고 복구 또는 담당자 인계가 가능하다. 복구 뒤 다시 확인한 내용만 제출된다. |

각 실행은 후보 커밋·작업 트리 상태, 앱 버전·설치본 해시, OS·아키텍처, 연결 레포 기준 커밋, 시나리오 ID, 사전 기대값, 관찰 결과, 증거 위치, 판정과 검증 담당자를 남긴다. 비공개 레포·파일·사용자 내용은 접근이 제한된 검증 기록에서만 다루고, 앱 로그·턴 통계에는 종류와 숫자만 남기는 기존 규칙을 유지한다.

판정은 `통과 / 실패 / 차단 / 미실행`이다. 두 OS에서 N1·N2·F1–F6을 각각 수행한다. 오류 주입으로 대체한 부분은 설치본 실기로 오인하지 않도록 별도 표기하고, 해당 복구 동작은 설치본에서도 확인한다. 수정 후 관련 실패 사례와 전체 정상 흐름을 다시 통과해야 한다. 소수의 실행 통과를 장기 무결함이나 AI 품질 보증으로 해석하지 않는다.

2026-10-20 실행 범위와 커밋·원격 대조 결과는 [구현 검증 기록](MVP-VALIDATION-2026-10-20.md)에 남겼다. 실제 AI 실행·로컬 git 원격·GitHub 모의 서버·macOS 개발용 패키지의 결과이며, 실제 GitHub 계정 간 협업이나 정식 설치본 베타를 통과한 것으로 세지 않는다.

후속 작업은 아래 검증 상태에서 실패·차단·미실행인 항목부터 이어간다. 필수 기준이 남으면 MVP 완료로 표시하지 않는다. 구현이 회귀하면 해당 변경만 분리해 되돌리고 작업 데이터와 기존 원장은 유지한다. 이미 전달된 원격 변경은 코드 복귀로 취소됐다고 보지 않고 별도 확인한다.

기능 확장은 위 기준을 통과한 뒤 베타에서 반복 관찰된 막힘을 근거로 하나씩 진행한다. 새 기능에도 사용자 가치, 실패·복구 경로, 기존 한 바퀴의 회귀 기준을 먼저 정한다.

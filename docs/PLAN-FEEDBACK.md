# 기능 제안

이해한 요청: 비개발자가 ColoNova Design 자체에 필요한 기능을 앱 안에서 제안하고, 제작팀의 GitHub 이슈로 전달한다. 설계는 Codex가 담당하고 구현은 OMP의 GLM 5.3과 GLM 5.3 Flash에 위임한다.

## 사용자 흐름

사이드바 바닥의 설정 위에 `기능 제안`을 둔다. 작업의 `제출`과 독립된 앱 전체 기능이며 프로젝트를 전환하거나 AI가 작업 중이어도 쓸 수 있다.

대화상자는 `어떤 기능이 있으면 좋겠어요?`(필수, 앞뒤 공백을 정리한 뒤 4,000자 이하)와 `지금 어떤 점이 불편한가요?`(선택, 2,000자 이하)만 받는다. 제목은 첫 줄에서 도구가 만든다. `보낼 내용 확인`을 누르면 읽기 전용 확인 화면과 `수정하기`, `제안 보내기`가 나온다. 확인 화면은 입력한 두 내용과 접수 대상, 함께 보내는 환경 정보를 설명한다.

접수 대상은 항상 `ColoNova Design 제작팀`이다. 전송 전에 `제안은 제작팀의 게시판에 올라가며 다른 사람이 볼 수 있어요. 앱 버전과 운영체제만 함께 보내요.`를 표시한다. 대화, 화면 캡처, 연결 프로젝트 이름, 소스, 로그, 연결 코드, 작성 이름은 자동 첨부하지 않는다. 첨부와 AI 요약은 이번 범위에 없다.

초안과 전송 시작 표시는 렌더러의 `window.localStorage`에 `colonova-design.feedbackDraft` 키로 보관하고 닫거나 다시 열어도 남긴다. 데몬 파일과 프로젝트 원장에는 쓰지 않는다. 저장소 사용이 불가능하면 메모리로 대체하여 이번 실행에서 작성과 닫기·열기를 지원하되 앱 재시작 뒤의 복구는 보장하지 않는다. 등록이 확인되면 초안을 비우고 `제안을 접수했어요`, `보낸 제안 보기`, `닫기`를 표시한다. 수정 내용이 없는 재클릭과 처리 중 중복 클릭은 두 번째 등록을 만들지 않는다.

## 접수 계약

`packages/protocol/src/feedback.ts`를 입력 한도와 결과 타입의 기준으로 둔다. `FeatureRequestInput = { request: string; context?: string }`. 공백만 있는 요청은 거절하고 두 필드는 앞뒤 공백을 정리한다. 새 클라이언트 명령은 `feedback.submit`이다. 프로젝트 디렉터리나 접수 저장소를 클라이언트가 지정하지 못한다.

공유 상수는 `FEATURE_REQUEST_MAX = 4000`, `FEATURE_CONTEXT_MAX = 2000`이다. 결과 타입 `FeatureRequestResult`는 `{ kind: "sent"; number: number; url: string } | { kind: "browser"; url: string; title: string; body: string } | { kind: "failed"; reason: "rejected" } | { kind: "uncertain"; url: string }`이다. 웹 API 이름은 `daemon.api.feedbackSubmit(input: FeatureRequestInput, commandId?: string): Promise<FeatureRequestResult>`로 고정한다.

접수 저장소는 기존 `RELEASES_REPO`를 참조한다. 이슈 제목은 `[기능 제안] `과 요청 첫 줄의 최대 80자를 붙인다. 본문에는 요청, 불편한 점(있을 때만), 앱 버전(알 수 있을 때), 운영체제만 싣는다. 등록에는 기존 데몬의 GitHub 클라이언트를 사용하되 연결 프로젝트나 개발자 알림의 상태를 변경하지 않는다. 새 자격 증명이나 공용 토큰을 앱에 넣지 않는다.

결과는 네 가지다.

| kind | 근거 | 화면 |
| --- | --- | --- |
| `sent` | 유효한 이슈 번호를 반환받음 | 접수 완료와 해당 이슈 링크 |
| `browser` | 토큰 없음·만료 또는 HTTP 401/403/404/410 | 아직 접수하지 않았음을 설명하고 `브라우저에서 마무리` |
| `failed` | HTTP 422 등 등록이 거절됐음 | 초안을 보존하고 수정 또는 다시 시도 |
| `uncertain` | 네트워크 단절·HTTP 5xx·잘못된 성공 응답 등 등록 여부 불명 | 접수 여부를 확인하지 못했다고 설명하고 `제안 목록 확인`; 자동 재전송 금지 |

`browser`는 제목·본문을 채운 고정 저장소의 새 이슈 URL을 제공한다. 기본 브라우저에서 사용자가 최종 등록해야 한다. GitHub 로그인이 필요할 수 있음을 미리 알리고, 브라우저를 여는 것을 접수 성공으로 취급하지 않는다. 긴 URL에 대비해 내용 복사와 빈 작성 페이지 링크도 제공한다. 외부 링크는 http(s), 고정 GitHub 목적지만 사용하며 기존 Electron의 외부 링크 처리를 따른다.

기존 명령 ID의 멱등 처리를 이용한다. `call`의 선택적 세 번째 인자 또는 동등한 전용 경로로 구현하되, 일반 명령의 ID 생성과 payload ID 무시 계약은 유지한다. 기존 기록은 데몬 재시작과 보존 기간 이후에는 사라지므로, 응답을 못 받은 요청을 초안의 ID만 믿고 다시 등록하지 않는다. 전송 직전에 초안에 전송 시작을 기록하고, 새로고침·앱 재시작 뒤 미완료 기록은 `uncertain`으로 복원한다. 전송 시작 뒤의 연결 단절·응답 시간 초과도 `uncertain`이다. 명시적 거절 후 수정·재시도만 새 ID를 만든다. `uncertain`에는 기존 내용의 재등록 버튼을 제공하지 않는다. 이전 내용을 표시하고 목록을 확인하게 하며, `목록을 확인했어요 · 새 제안 작성`은 빈 양식으로 새 요청을 시작한다. 브라우저 경로는 작성 페이지 링크를 누른 시점부터 확인 불가 상태로 남긴다. 브라우저가 필요하다는 API 결과만으로 전송 시작 표시는 남기지 않는다.

## 화면 계약

기존 `.nx` 토큰, 버튼, 모달 훅을 사용한다. 사용자 문장은 `labels.ts`의 `L.feedback`에만 둔다. 480px 안팎의 한 장으로 만들고 작은 창에서는 화면 여백 안에 맞추며 본문만 스크롤한다. 입력란은 위아래로 배치하고 그림·카드·새 테마를 추가하지 않는다.

작성·확인·전송 중·완료·브라우저 필요·명시적 실패·확인 불가 상태를 모두 표현한다. 필수 입력과 길이 오류는 입력란에 연결하고 전송 상태는 읽기 도구에 알린다. 모달은 초점 가두기·닫힌 뒤 초점 복원·Esc를 지원한다. 전송 중에는 필드와 전송 버튼을 잠그고 한글 조합 중 Enter로 등록하지 않는다. textarea의 Enter는 줄바꿈이다. 좁은 창의 사이드바에서 열면 서랍을 닫아 모달 뒤에 겹치지 않게 한다. 기존 모달 겹침과 전역 단축키 검사에 포함한다.

## 위임과 검증

- GLM 5.3: protocol의 입력/결과 계약, GitHub 오류 상태와 응답 검증, 데몬 접수·라우팅, 명령 ID 재사용을 포함한 웹 API 연결, 관련 단위 시험.
- GLM 5.3 Flash: 위 계약을 사용하는 모달·사이드바·셸 연결·문장·CSS, 사용 설명서와 개발자 안내의 최소 수정.
- Codex: 설계, 통합 검토와 검사 실행, 필요 수정의 재위임. 외부 저장소에 실제 시험 이슈를 작성하지 않는다.

검증은 고정 접수 목적지, 입력 제한, 한글 URL 인코딩, 토큰 없음·권한 부족·등록 거절·네트워크 불명확, 유효하지 않은 성공 응답, 같은 명령 ID에 대한 중복 방지와 초안 보존을 중심으로 한다. 문장 규칙 시험, 타입 검사, 빌드와 로컬 화면 점검을 수행한다. 앱과 데몬이 함께 배포되므로 프로토콜 버전은 올리지 않는다.

기본 브라우저 경로에서는 GitHub 계정과 저장소 접근 권한이 필요할 수 있다. 별도 계정 없이 모든 사용자에게 확실한 접수를 보장하려면 제작팀의 접수 서버가 필요하며 이번 구현에는 포함하지 않는다.

# Confluence 기획서 동기화 — 실현 가능성 분석과 착수 계획

2026-10-18. 기획 전용 올인원 도구 스펙(사용자 제공, 2026-10-18)을 현재 코드 기반 위에서 전수 분석한 기록이다.
외부 조건은 같은 날 Confluence 실측으로 확인했다. 분석·소스는 아래 「출처」 절에 적는다.

## 한 줄 결론

스펙 그대로 가능하다. 1 · 2단계는 레포 안 선례(감독자 폴링 · 원장 · 키체인 · 보조 브랜치 · 제출 거름)의
복제다. 사전 검증은 앱 자체 Confluence 인증 하나로 좁혔고, 발행의 앵커·매크로 보존은 2026-10-18 실측으로
답이 나왔다 — **발행은 저장 포맷 절 스플라이스로 한다.**

## 목표와 모델 (스펙 요약)

- ColoNova Design 을 기획 전용 올인원 도구로 — 기획서 쓰기부터 데모 화면까지 이 도구 하나에서.
- Confluence 는 "게시판"(모두가 보는 공식본), CDP 레포의 기획서 폴더는 "내 책상"(작업본). 사본은 두 벌뿐.
- 가져오기는 자동, 발행은 버튼. 양방향 동기화.
- 판 번호 충돌: 가져올 때 판을 적어 두고, 발행할 때 판이 바뀌었으면 멈추고 차이를 보여 준다.
  코멘트는 판을 안 올리므로 따로 가져온다.
- 문서와 화면을 한 레포(CDP "방")에 두는 이유 — AI 가 둘을 같이 봐야 "이 화면이 저 정책과 맞나" 를 본다.
- 문서 종류: 정책서는 필수, 기능설계서는 선택. 기획팀 여러 명이 함께 쓴다.

## 범위 결정

- **2026-10-18 사용자 결정 — 분석은 일단 뺀다.** 분석 9종(미결 · 어긋남 · 번짐 · 코멘트 · 모순 · 용어 ·
  커버리지 · 판 현황 · 결정 기록)과 도구 벤치마크 기능(Jama · Copilot4DevOps · QVscribe · ChatPRD · Rovo ·
  Delibr · Kiro · Notion 대응)은 전부 나중으로. 벤치마크는 분석 9종의 재포장이라 함께 빠진다.
- 남는 것: 기획서 관리(CRUD) · Confluence 동기화(가져오기 · 발행) · 데모 화면(지금 그대로).
- 3단계(화면 ↔ 문서 잇기)는 축소 — 화면 변경 기록에서 문서를 열어 고치는 **수동** 흐름까지만.
  "이 결정이 닿는 문서 3곳" 같은 자동 매칭은 분석 의존이라 나중으로.
- 분석을 다시 붙일 때는 1단계의 문서 원장 위에 얹는다. 순서만 뒤집히지 구조는 안 바뀐다.

## Confluence 실측 (2026-10-18, 세 차례)

개인 스페이스(~63dcb628491b20ef64b9cd71, 정인권)에 스크래치 페이지를 만들어 전 구간을 돌리고 지웠다.

| 페이지 복제(첨부 동반) | 통과(02:07 KST) — 새 ID · **판 1 재시작** · 첨부 새 ID 로 동반 · 내용 동반 |
| 페이지 이동 | 통과 — **ID 불변 · 판 미증가**, 트리 위치만 변경. 원장은 ID 로 추적하면 이동이 흔들지 않는다 |
| 저장 포맷 전체 재발행 | 통과 — 매크로 · 첨부 보존, 판 증가. 정본 전체 발행도 무손실 |

실측에서 나온 설계 제약:

- **발행 경로는 저장 포맷 절 스플라이스다.** 마크다운 왕복은 앵커와 매크로를 잃는다(2차 실측). 도구의
  정본은 저장 포맷(XML) 원문이고, 발행은 정본에서 해당 절만 갈아 끼워 넣는 방식이다 — 앵커 마커 보존과
  매크로 복원이 실측으로 확인됐다(01:58 KST, 판 3).
- **낙관적 잠금은 앱의 몫이다.** MCP 갱신 도구는 판을 자동으로 올려 덮어쓴다. 앱은 직접 REST 를 쓰고
  발행 전에 판을 비교해야 한다 — REST PUT 은 판이 틀리면 409 로 거절한다(스펙 §5 와 일치).
- 코멘트는 판을 안 올린다(CONFCLOUD-82395) — 코멘트는 별도 가져오기. 스펙 설계가 맞다.
- 기존 문서 위치: COLO 스페이스 `프로젝트/8.8 ColoNova/`(01.시스템분석~10.솔루션 + 99.Archive),
  개인 스페이스 `📁 01. ColoNova 설계`(Workflow·Policy 노트, SAP EWM 조사, 화면 표준·Zone·ADR,
  NOVA-972, 데이터 모델 SSoT), PROD 스페이스(제품 기획 체계 · 기획 리뷰). 데이터 모델 SSoT 페이지에는
  이미 "기획 AI 는 Atlassian MCP 로 이 페이지를 fetch 하라"는 안내가 있다.

## 리스크와 사전 검증

1. **앱 자체 인증(1단계 첫 검증)** — 실측은 MCP 세션 자격 증명 경로다. 앱 자체 REST 클라이언트가 기본
   인증(이메일+API 토큰)으로 같은 권한을 내는지 첫 주에 검증한다. 기획자 각자 자기 토큰 — "어떤 토큰도
   우리가 수집하지 않는다" 정책과 합치고, 화면 쪽 코드에는 절대 전달하지 않는다(지금의 연결 코드와 같다).
2. **인라인 코멘트 닻 — 실측으로 닫혔다(2차).** 마크다운 절 발행은 앵커 마커를 떼고, 저장 포맷 절 발행은
   보존한다. 설계 규칙은 하나 남는다 — 앵커가 든 문단은 정본(저장 포맷)에서 갈아 끼운다.
3. 속도제한 · 문서 크기 — 정책서 87쪽 + 기능설계서 73쪽은 페이지 단위 가져오기로 충분한 규모. 폴링은
   감독자 간격 패턴을 재사용.
4. 다수 사용자 동시 편집 — 판 충돌 흐름이 담당하고, 문서 단위 잠금 표시(원장)로 완화.
5. 문서 갱신 부담 — README · GUIDE(설정 연결 쪽 + 기획서 절) · DEVELOPERS(동기화 · 발행 · 충돌 · 토큰 ·
   환경 변수 · 테스트 절) · ux-survey 개정 이력을 코드와 같은 변경에서 고친다(AGENTS.md 규칙).
6. 코멘트 해결 상태 — 바닥글 · 인라인 생성, 답글, 한글 텍스트 앵커 매칭(두 번)은 실측으로 열렸다(2026-10-18).
   남은 것: 인라인 코멘트의 해결 상태를 REST 로 읽고 바꾸는 길, 코멘트 수정 가능 범위 — 2단계(코멘트
   달기) 착수 전에 앱 자체 클라이언트로 검증한다.
7. 첨부 내용 왕복 · 휴지통 복구 — 업로드 · 복제 동반 · 메타는 실측으로 열렸으나 다운로드 내용 검증과
   삭제 복구(restore)는 도구 경로가 없어 미실측이다. 1단계(다운로드) · 2단계(복구) 착수 때 앱 자체
   클라이언트로 REST 로 검증한다.

## 미정 3가지 — 권고 (스펙 §10)

1. **발행 시점** — 화면 제출과 발행은 분리(발행은 버튼). 권장 순서는 문서 발행 → 화면 제출이되 강제하지
   않는다. 화면이 먼저 정해진 결정은 수동 화면→문서 흐름이 메운다.
2. **기획서 폴더 주인** — 폴더의 존재(이름 · 위치 · 제출 제외 규칙)는 개발팀이 레포에 정하고, 내용은
   기획팀이 앱 경로로 개발 리뷰 없이 고친다. A 안이면 개발팀 소유는 거름 규칙 하나뿐이다.
3. **발행 판 단계** — 기본은 "가져온 판과 같은 단계의 개정"(0.8→0.8), 승급(→0.9)은 발행 확인 창에서
   사람이 명시적으로 고른다. 자동 승급 없음.

## 단계별 착수 목록

- **1단계(읽기 — 순수 동기화 + 뷰어)**: REST 클라이언트 · 키체인 토큰 항목 · 설정 연결 쪽 입력 ·
  저장 포맷 보존 가져오기(트리 → 폴더, confluence.json 원장) · 폴더 A 안 · 뷰어. 아키텍처 변경 0.
- **2단계(쓰기)**: 절 단위 편집기 · 저장 포맷 절 스플라이스 발행 · 판 충돌 흐름(§5 UI 그대로) · 코멘트 달기.
- **3단계(축소)**: 화면→문서 수동 반영 흐름.
- **나중(분석 복귀 시)**: 1단계 원장 위에 분석 9종과 벤치마크 대응을 얹는다.

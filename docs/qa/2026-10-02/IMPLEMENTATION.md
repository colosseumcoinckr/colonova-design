# QA 후속 구현 결과

2026-10-02 · 근거: [실사용 QA 보고서](REPORT.md)

사용자 요청에 따라 오케스트레이터가 범위·검토·실제 앱 검증을 맡고, GPT-6.1-Sol이 아래 세 가지 P1 수정을 구현했다. 이 문서는 첫 번째 구현의 기록이며, 당시 전체 테스트 1,059개, 타입 검사, 빌드가 통과했다. 이후 구현한 요청별 결과 카드·화면별 확인·제출 검토와 최신 검증 결과는 [후속 UI 개선 결과](UI-IMPROVEMENTS.md)에 기록한다.

| 순서 | 구현 대상 | 검증 기준 |
| --- | --- | --- |
| 1 | 대화의 중복 식별, 핀 요청 기록, 모델 정보 | 일반 A/B → 핀 C → 홈 → 재열기 → 내보내기에서 질문·핀·응답의 대응을 유지한다. 같은 대화의 행은 하나이며 확인되지 않은 모델을 기본값으로 표시하지 않는다. |
| 2 | 자동 검사의 진입 조건과 완료 표시 | 변경 없는 요청에 자동 수정을 붙이지 않는다. 실제 변경 뒤의 자동 검사는 유지한다. 실행 종료와 수정 성공을 구분하며 검사 경로는 실제 화면과 일치한다. |
| 3 | 제출 대상 집계 | 자동 최신화를 사용자 변경으로 세지 않는다. 화면 밖 항목의 단위와 설명이 실제 근거에 맞고 프로젝트 전체 제출 범위는 유지한다. |

## 대표 검증 시나리오

1. 새 대화 하나에서 “변경·제출 없이 첫 번째 응답 A만 답해 주세요”, 이어서 같은 조건의 B를 보낸다. 서비스 선택 화면 제목에 핀을 찍고 “수정하지 마세요” 메모와 같은 조건의 C를 보낸다. 재열기·앱 재실행·내보내기 모두 A/B/C 질문과 답변이 대응하며 대화 행이 늘어나지 않아야 한다.
2. 이미 다른 작업의 변경이 있는 프로젝트에서도 위 설명 요청은 추가 수정을 유발하지 않아야 한다. 반대로 이번 요청에서 실제 파일 내용이 바뀌면 자동 검사 대상으로 삼는다. 단순히 핀을 찍었거나 프로젝트 전체에 변경이 남아 있다는 사실만으로 수정 검사를 시작하지 않는다.
3. 자동 최신화만 있고 사용자 변경이 없으면 제출할 변경이 없다고 표시한다. 사용자 수정 화면 하나와 최신화 여섯 번이면 최신화를 ‘화면 밖 변경 6건’으로 표시하지 않는다. 화면에 연결되지 않은 최종 변경 파일이 두 개라면 실제 파일 두 개를 근거로 설명하며 기록 횟수와 혼동하지 않게 단위를 밝힌다.

## 작업 방식

- 기존 미커밋·미추적 파일을 포함한 작업 상태를 별도로 보관했다. 기존 변경을 취소하거나 대체하지 않는다.
- Sol 한 명이 순서대로 수정하고 별도 Sol 검토자가 변경을 검토했다. Electron 조작과 실제 앱 재검증은 오케스트레이터가 맡았다.
- 중복 행의 원인을 조사해 대화 ID 연결 누락과 홈 생성 경합을 구분했다. 제품 문구는 기존 `labels.ts` 규칙을 따랐다.
- 관련 회귀 테스트, 타입 검사, 빌드와 실제 앱 재검증을 수행했다. 연결 프로젝트의 기존 작업을 제출·복구·삭제하거나 외부 메시지를 보내지 않았다.

## 실제 앱 검증에서 추가로 확인한 것

첫 구현은 전체 테스트 1,055개와 타입 검사·빌드를 통과했다. Electron을 새로 시작하고 일반 A/B와 핀 C를 보낸 뒤 프로세스를 다시 시작해, 질문·핀 메모·답변이 재열기와 내보내기에서 유지되는 것을 확인했다. 변경 없는 핀 요청에 자동 수정이 붙지 않았고, 제출 창에서 자동 최신화 여섯 건이 화면 밖 변경으로 표시되지 않았다.

이 과정에서 다음 두 경로를 더 발견해 보완했다.

- 홈에서 대화를 만든 직후 아직 갱신되지 않은 UI 상태를 읽어 빈 대화를 하나 더 만드는 경합. 전송 성공 후 홈 초안이 남는 문제도 같은 흐름에서 확인했다.
- 저장된 대화의 모델 조회가 살아 있는 세션만 지원해 ‘확인하는 중’으로 계속 남는 문제. 저장된 선택을 조회하고, 기록이 없는 과거 대화는 확인되지 않았음을 명확하게 표시한다.

근거: [첫 구현의 재시작 뒤 대화](implementation/abc-after-restart.png), [내보낸 대화](implementation/abc-after-restart.md), [제출 요약](implementation/submit-summary.png). 첫 번째 이미지는 모델 조회 보완 전의 중간 상태다.

## 구현 내용

| 대상 | 원인과 변경 |
| --- | --- |
| 대화·핀·모델 | 앱 대화 ID와 제공자 대화 ID를 프로젝트별로 연결해 저장한다. 핀 요청을 일반 내부 지시로 오인해 버리던 필터를 수정했다. 저장된 대화의 모델 선택을 실행 중인 세션 없이 읽고, 정보가 없으면 확인되지 않았다고 표시한다. |
| 홈 전송 | 대화 생성 직후 오래된 목록을 읽어 두 번째 빈 대화를 만들던 경합을 제거했다. 전송 성공 때 원래 초안을 명시적으로 비우되, 새로 입력한 내용은 보존한다. |
| 자동 검사 | 요청 전후 실제 파일 내용을 비교해 이번 요청이 만든 변경으로 진입 여부를 판단한다. 기존 미제출 변경만으로 수정을 시작하지 않는다. 재검사 성공·미확인·남은 문제·중단을 구분하고 첫 화면 검사 경로를 바로잡았다. |
| 제출 요약 | 자동 최신화 기록 횟수 대신 실제 제출할 최종 파일 차이를 집계한다. 되돌려 사라진 변경과 자동 최신화를 제외하고, 남은 파일을 관련 요청·화면에 연결한다. |

검토 중 프로젝트 간 ID 혼동, 선택 해제 뒤 이전 모델 값 재등장, 대화 삭제 실패 처리도 보완했다. 제품 코드·테스트·사용자/개발자 안내의 이번 작업 차이는 시작 시점 보관본 대비 38개 파일이며, QA 문서·증거는 별도다. Electron 데스크톱 소스는 수정하지 않았다.

변경 범위는 [파일 목록](implementation/changed-files.txt)에 남겼다. 시작 시점 보관본은 로컬 `/tmp/colonova-orchestration-20261002-172147/files/`에 있으며, `/tmp` 정리 뒤에는 유지되지 않을 수 있다.

내보낸 대화 원본에는 연결 서비스의 기존 로고 문구가 포함된다. 제품명 검사에서 이 원본 증거 파일 하나만 예외로 두었으며, 원본을 변조하거나 QA 디렉터리 전체를 제외하지 않았다. 기존 형식 검사 부채를 일괄 정리하지 않았으므로 전체 린트 통과를 주장하지 않는다.

## 남은 범위와 다음 작업

- 모든 기능의 전체 종단간 검증을 완료한 것은 아니다. 실제 제출·복구·삭제, 외부 공유, 모든 제공자의 실제 실행은 이번 검증에 포함하지 않았다. 실제 모델 확인은 Luna에 한정되며 다른 제공자 경로는 자동 검사 범위다.
- 저장 체계 도입 전에 생긴 별칭 관계나 빈 대화는 자동으로 추정·삭제하지 않는다. 기록 저장 위치에 쓸 수 없는 환경에서는 재시작 뒤 복원을 보장할 수 없다.
- 이 단계에서는 새 대화의 사이드바 제목이 갱신돼도 열린 대화의 머리말이 ‘새 화면’으로 남는 현상을 관찰했다. 후속 UI 구현에서 열린 대화의 이름 조회를 보완했다.
- 당시 제안한 **요청별 결과 카드 → 화면별 검토 현황 → 제출 전 검토 화면**은 후속 구현을 완료했다. 최신 검증 범위와 남은 과제는 [후속 UI 개선 결과](UI-IMPROVEMENTS.md)를 따른다.

기존 작업을 보존했으며 커밋·푸시·릴리스·연결 프로젝트 제출은 수행하지 않았다. 앱은 최종 소스로 실행해 둔 상태다.

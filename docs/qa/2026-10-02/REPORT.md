# ColoNova Design 실사용 점검과 개선 제안

2026-10-02 · macOS · `pnpm dev:desktop` · 연결 프로젝트 `colonova-cdp`

이 문서는 **수정 전 관찰 기록**이다. 이후 사용자가 구현 위임을 요청했으며, 후속 작업과 검증 결과는 [구현 계획·결과](IMPLEMENTATION.md)에 기록한다.

**17시 재검증 반영:** 중복 대화 행 사이의 기록 불일치와 두 번째 행의 내보내기에서 핀 질문 누락을 확인했다. 자동 검사의 완료 표시 문제를 추가했다. 첨부 용량 제한은 정상으로 정정했다.

**권장 방향: 사용자가 요청한 것, 실제 바뀐 것, 개발자에게 보낼 것을 화면 단위로 연결한다.** 현재의 대화·미리보기 구조와 ‘말하고 · 찍고 · 제출’ 흐름을 유지하면서, 결과를 확인하고 판단하는 경험에 투자하는 편이 좋다.

요청 해석: 실행 중인 Electron 앱을 Computer Use로 직접 점검하고, 테스트 결과와 우선순위별 기능·UI·UX 제안을 제공한다. 사용자가 선택한 범위에 따라 제품 코드는 수정하지 않았다.

## 이번 점검의 범위

실제 앱의 클릭, 입력, 파일 선택창, 접근성 트리, 스크린샷으로 확인했다. [홈 화면](home.png) 등 1차 스크린샷과 [재검증 근거](retest/)를 보관했다. 문서와 일부 소스는 관찰 결과를 해석하는 데 사용했다. 아래의 ‘확인’은 해당 조작에서 기대한 결과를 보았다는 뜻이며, 기능 전체의 무결함을 뜻하지 않는다.

**아래 표의 기능 범위를 검토했지만 전 기능 E2E 통과를 선언할 수는 없다.** 활성 프로젝트에는 기존 미제출 작업이 있었고, 등록 프로젝트는 하나였다. 실제 제출·되돌리기·삭제·초기화, 새 계정 연결, 개발자 코멘트·병합은 실행하지 않았다.

1차 점검에는 앱 재시작과 코드 갱신이 섞였다. 사용자의 “다시해보자” 이후 재검증에서는 17:03부터 제품 소스와 주요 문서 296개 파일의 SHA-256을 기준으로 비교했고, 주요 결함 재현과 내보내기 완료까지 변경이 없었다. 앱 재시작도 관찰하지 않았다. HEAD는 `2baeef9f`였으나 미커밋 변경이 많은 개발 실행이므로 릴리스 빌드 인증은 아니다. 이 비교는 ColoNova Design 저장소를 대상으로 하며 연결 서비스 저장소 전체의 무변경을 증명하지 않는다.

시험 대화는 1차 `QA 점검입니다…`와 2차 `[재검증 A]…`를 남겼다. 2차 대화는 새 대화를 한 번 만들었는데 같은 제목의 행이 두 개 나타났다. 두 번째 행은 `QA 재검증 · 일반 A/B + 핀 C`로 이름을 바꿨다. 초안은 비웠으며, 문서·화면 첨부는 전송하지 않고 제거했다. 테마는 Claude, 미리보기는 PC·100%이고 마지막 확인 화면은 WMS 입고 목록이다. 기능 제안·제출은 보내지 않았다. 대화 내보내기 파일은 보고서 근거 폴더에 저장했다.

## 먼저 해결할 세 가지

### 1. P1 — 중복 대화 행 사이의 기록이 다르고 한쪽 내보내기에 핀 질문이 없다

**재현 절차:** 새 대화에서 다음 순서로 요청했다. 모든 요청에 파일·화면·설정 변경과 제출을 하지 말라는 조건을 넣었다.

1. 일반 요청 A: 정확히 “첫 번째 응답 A”만 답하도록 요청.
2. 일반 요청 B: 정확히 “두 번째 응답 B”만 답하도록 요청.
3. 이 시점에 사이드바의 두 A 대화를 각각 열었다. 양쪽 모두 A·B 질문과 답변이 정상으로 남았다.
4. 첫 번째 행으로 돌아와 서비스 선택 화면의 제목에 핀을 찍고, 메모 `[재검증 C] 수정하지 마세요.`와 정확히 “세 번째 응답 C”만 답하라는 요청을 보냈다.
5. 두 번째 행을 열어 표시된 기록을 확인하고, Markdown으로 내보냈다.
6. 홈으로 나간 뒤 첫 번째 행 자체를 다시 열었다. 이쪽은 C 질문과 핀 메모가 유지됐다.

**실제 결과:** 첫 번째 행의 실시간 화면과 홈 경유 재열기에서는 A·B·C가 각각 표시됐다. 두 번째 행에서는 C 질문과 핀 메모가 보이지 않고 **B 질문 바로 아래 C 답변**이 표시됐다. B 답변은 `작업 과정` 안으로 들어갔다. 내보낸 Markdown에도 C 질문이 없고 B 뒤에 B·C 답변과 자동 검사 후 답변이 이어졌다. 일반 두 턴은 정상이었으므로 이번 재현 범위는 **핀 요청과 그 뒤 자동 검사가 포함된 대화**다. 핀만의 영향과 자동 검사의 영향은 아직 분리하지 못했다. **두 행이 동일 세션을 가리키는지도 미확인**이므로, 동일 세션의 저장·복원 결함인지 별도 세션 사이의 표시·연결 결함인지는 아직 판정하지 않는다.

**함께 관찰한 문제:** 새 대화를 한 번 만들었는데 같은 제목의 행이 두 개 나타났다. 첫 번째 행은 응답별 경과 시간을 보여줬고 두 번째에는 그 시간이 없었다. 모델 표시도 첫 번째의 `GPT-6-Luna · 간단히`와 두 번째의 `GPT-6.1-Sol · 보통`이 달랐다. 실제 호출 모델이 바뀌었다고 단정하지 않는다. 한 행의 이름을 바꿔도 다른 행의 이름은 그대로였다.

**사용자 영향:** 질문과 답변의 대응, 수정·분기 기준, 외부로 보관한 기록을 신뢰하기 어렵다. 두 번째 행의 UI와 내보내기에는 C 질문이 없지만 첫 번째 행에는 남아 있었다. 원본 데이터 삭제로 판정하지 않는다.

**최소 개선:** 사용자 요청·핀·자동 검사 턴을 구별하되 원래 요청별 묶음을 저장과 복원에서 보존한다. 대화 목록의 중복 식별과 모델 정보 복원도 함께 조사한다. 요청 식별자와 기록 결합은 조사 후보이며 확정 원인은 아니다.

**완료 조건:** 일반 A → 일반 B → 핀 C → 홈 → 재열기 → 앱 재실행 → 내보내기에서 세 질문·핀 메모·세 응답의 대응이 유지된다. 자동 검사는 C에 종속된 과정으로 남고, 기존 B 답변을 덮어 묶지 않는다. 대화 행은 하나이고 모델 표시는 확인된 세션 정보와 일치해야 한다.

### 2. P1 — 설명만 요청했는데 자동 수정 지시와 ‘고쳤어요’가 나온다

**관찰:** 위 C는 명시적인 변경 금지 요청이었다. 첫 응답 뒤 자동 `화면 확인` 카드가 나타났고, 상세에는 `/index`의 404 두 건과 “아래를 고친 뒤 답해 주세요”가 표시됐다. 보이는 미리보기는 정상적인 `/` 서비스 선택 화면이었다. 이후 같은 C 응답이 한 번 더 나오며 카드는 `AI가 고쳤어요`, `하실 일은 없어요`로 완료됐다. AI의 작업 과정에는 기존 변경 금지 조건을 따르겠다는 내용이 있었다.

**소스 확인:** 현재 `GateCard`의 완료 문구는 `fixing`이 false이면 ‘AI가 고쳤어요’를 표시한다. 이 컴포넌트의 표시 조건에는 수정 diff나 재검사 통과 여부가 없다. 따라서 이 문구만으로 수정 성공을 증명할 수 없다.

**판정과 한계:** 변경 금지 요청에 자동 수정 지시가 생기고, 성공 근거 없이 수정 완료처럼 표현되는 흐름을 재현했다. 실제 연결 파일 수정이나 404 해결은 확인하지 못했다. `/`와 `/index`의 차이는 경로 정규화 조사 단서이며 404의 원인으로 확정하지 않는다.

**최소 개선:** 설명·관찰 요청은 자동 수정을 시작하지 않게 한다. 검사 발견, 수정 시도, 실행 종료, 재검사 통과를 서로 다른 상태로 표시한다. 실제로 고치지 않았다면 ‘확인했어요 · 변경 없음’, 해결을 확인하지 못했다면 ‘문제가 남아 있어요’로 표시한다.

**완료 조건:** 동일한 변경 금지 핀 요청에는 수정 지시가 생기지 않는다. 수정 요청에서도 결과를 검증한 경우에만 성공 표시를 하고, 실패·중단·변경 없음 상태를 구분한다. 화면 검사 대상 경로가 사용자가 보고 있는 경로와 일치해야 한다.

### 3. P1 — 제출 요약의 ‘화면 밖 변경’은 실제 변경 내용으로 설명해야 한다

**관찰:** 1차 제출 창에서 `WMS 입고 목록 · 작업 이어 보관`과 `화면 밖 변경 4건 → 5건`을 봤다. 재검증에서는 화면은 여전히 1개이고 화면 밖 변경은 6건이었다. 작업 기록에는 10:23의 작업 이어 보관과 최신화 기록 여섯 개가 있었다. 가장 최근 최신화는 17:05였다. 제출 창에서 6건의 내용을 펼칠 수 없었다.

**소스 확인:** `outsideChanges()`는 화면 목록과 대응되지 않는 작업 기록의 수를 센다. 이 계산 자체에는 최신화 같은 기록 종류를 제외하는 조건이 없다. 따라서 이 숫자를 파일 수나 실제 제출 diff의 변경 수로 읽으면 안 된다.

**사용자 영향:** 자동으로 가져온 내용과 내가 만든 내용을 구분하기 어렵고, 무엇을 함께 제출하는지 충분히 판단할 수 없다.

**최소 개선:** ‘이번에 전달되는 최종 변경’을 기준으로 요약한다. 화면별 변경 이유와 결과를 한 줄씩 보여주고, 공통 스타일·설정 등 화면에 직접 묶이지 않는 내용도 펼칠 수 있게 한다. 자동 최신화는 별도 활동으로 접고, 기록 수를 변경 수처럼 부르지 않는다.

**완료 조건:** 화면 수는 최종 변경이 남은 고유 화면 기준으로 센다. 화면 밖은 설명 가능한 변경 항목으로 보여주며 기록 횟수를 사용하지 않는다. 자동 최신화만 있고 사용자 변경이 없다면 ‘제출할 변경이 없어요’로 표시한다. 되돌린 변경은 최종 상태에 맞게 정리한다.

| 핀 선택 | 입고 번호 입력칸 클릭 | 확인. 요소명·화면명·메모 입력이 있는 말풍선 표시 |

| 핀 제거 | 두 번째 핀만 제거 | 확인. 첫 번째 메모 유지 |
| 핀 AI 요청 | 첫 번째 핀과 설명 요청 전송 | 확인. 검색칸 역할 응답, 실행 중 ‘보냄’ 핀, 완료 후 제거. 질문 자체에 요소명이 있어 AI의 시각적 식별 정확도를 증명하지는 않음 |

| 첨부 크기 제한 | 8MiB+1B 파일 선택 | **재검증 통과.** 파일 거절과 “8MB 보다 큰 파일은 보낼 수 없어요” 안내 확인. [증거](retest/attachment-limit.png) |

## 제품을 더 강하게 만들 제안

아래는 구현 완료 주장이나 확정 일정이 아닌 설계 제안이다. 이미 있는 핀·비교·기록·지침·내보내기를 기반으로 확장한다.

| 순서 | 제안 | 사용자가 얻게 되는 경험 | 최소 범위 / 완료 모습 |
| --- | --- | --- | --- |
| 1 | **요청별 결과 카드** | ‘검색창 추가 요청’ 아래 변경된 화면·변경 이유·전후 비교·추가 수정이 함께 보임 | 한 요청과 결과를 연결. 설명만 한 답에는 변경 카드를 만들지 않음. 재열기해도 동일 |
| 2 | **제출 전 검토 화면** | 무엇이 달라졌는지 보고 개발자에게 전달할 설명까지 마무리 | 화면별 최종 변화, 화면 밖 변화의 설명, 받는 사람, 내 메모. 현재의 프로젝트 전체 제출 원칙 유지 |
| 3 | **화면 목록과 검토 현황** | 긴 대화에서 결과를 찾지 않고 화면 이름·미리보기 이미지로 이동 | 기존 화면 선택기에 최근 수정·즐겨찾기·미확인 상태 추가. PC·휴대폰별 확인 상태 표시 |
| 4 | **현재 맥락이 보이는 입력창** | 보내기 전에 AI가 볼 화면·크기·핀을 바로 이해 | `입고 목록 · 휴대폰 · 선택 2곳`을 표시하고 각 항목 제거·이동 지원. 현재 확인된 요소명 칩을 유지하고 화면·크기를 함께 표시 |
| 5 | **검토 시나리오 저장** | ‘입고 검색 결과 없음’처럼 확인하던 상태로 다시 돌아옴 | 화면·크기·재현 조작을 이름으로 저장. 먼저 로컬 검토용으로 제공하고 지원하지 않는 상태는 명시 |
| 6 | **프로젝트별 요청 시작점** | 빈 입력창에서 무엇을 말해야 할지 고민하지 않음 | 최근 화면에서 `빈 상태 추가`, `휴대폰 확인`, `문구 다듬기` 등 구체적인 요청 초안을 생성. 클릭 즉시 실행 대신 수정 가능한 초안으로 담기 |

첫 세 가지가 다음 구현 묶음의 중심이다. 그 전에 위 P1의 대화 대응, 자동 검사 상태, 제출 집계를 수정하고 재검증해야 한다. 그 기반이 흔들리면 새 결과 카드도 잘못된 정보를 더 보기 좋게 보여줄 뿐이다.

## UI·UX를 다듬을 구체적인 방향

- **휴대폰 검토를 결과에 남긴다.** 1차에서 연결 서비스의 OMS·WMS·Setting 카드가 좁게 눌리고 글자가 겹쳤다. 이는 ColoNova 셸과 별개인 연결 화면 문제다. 화면마다 PC·휴대폰의 확인 상태를 두고, 해당 크기의 핀 요청과 전후 비교로 이어준다. 미검사는 정상으로 표시하지 않는다. [관찰 화면](mobile-preview.png).
- **지금의 따뜻한 색과 대화/화면 2열은 유지한다.** 우선 바꿀 것은 정보의 배치다. 상단에 긴 요청 원문을 그대로 반복하기보다 짧은 작업 제목과 현재 화면을 분리하고, 원문은 대화에 둔다.
- **기록의 기본 목록은 사람이 만든 변화부터 보여준다.** ‘최신 내용을 가져왔어요’는 자동 활동 묶음으로 접고, 각 기록에서 영향을 받은 화면으로 이동하게 한다.
- **빈 홈을 다음 행동과 연결한다.** 입력창 아래에 최근 수정 화면과 ‘이어서 확인’ 하나를 두고, 진행·최근 활동이 모두 비어 있으면 빈 그룹을 간결하게 줄인다.
- **실행 피드백은 사용자의 동사로 쓴다.** 이번 설명 요청에서도 상태는 ‘만드는 중’, 제출 비활성 이유는 ‘AI가 고치는 중’이었다. 확인 중·만드는 중·검토 중을 실제 단계에 맞춘다. 모르는 단계는 꾸며내지 않는다.
- **오류 문장에는 가능한 다음 행동을 붙인다.** 시험 알림의 원문 오류 코드는 상세 정보로 보내고, 개발 실행에서 지원이 안 되는 경우와 OS에서 차단한 경우를 구분한다.
- **모델 선택은 선택 결과를 신뢰할 수 있게 한다.** 공급자·모델·생각 시간을 명확히 유지하고, 확인되지 않은 상태의 잠깐 기본값 표시를 줄인다. 사용량은 이번 앱만의 비용처럼 해석되지 않도록 계정 범위를 밝힌다.

## 남은 주요 E2E 검증

다음은 우선 실행할 통합 시나리오다. 전체 완료 판정에는 위 표의 모든 미검증 항목도 각각 확인해야 한다. 코드 변경이 멈춘 빌드와 버려도 되는 별도 연결 프로젝트 두 개에서 진행하는 것이 적절하다.

1. 초대 가져오기 → 프로젝트 준비 → 간단한 화면 생성 → 핀 수정 → PC·휴대폰 확인 → 전후 사진 비교.
2. 제출 → 개발자 코멘트 → AI 반영 → 재제출 → 병합 → 다음 작업. 실제 개발자 알림·외부 게시가 포함되는 구간은 수신처가 정해진 테스트로 별도 실행한다.
3. 이전 화면 복구 → 복구 기록 확인, 대화 수정·분기, 핀 질문을 포함한 내보내기 무결성, 프로젝트 전환 중 실행·초안·미리보기 유지.
4. 네트워크 끊김, 실행 중 멈추기, 미리보기 종료, 앱 재시작, 첨부의 다른 형식·개수 제한을 각각 재현하고 입력과 결과의 보존을 확인한다.
5. 패키징된 macOS 앱에서 알림·업데이트를 검증하고, Windows는 별도 실제 환경에서 실행한다.

이 보고서는 [사용 설명서](../../GUIDE.md)의 전체 계약을 대체하지 않는다. 특히 개발 중 UI에서는 대화 내보내기와 ‘지켜 줄 것’이 확인됐으나, 점검 시 읽은 개발자 문서에는 아직 UI가 없다는 설명이 남아 있었다. 출시 전에는 해당 문장을 현재 구현과 맞춰야 한다.

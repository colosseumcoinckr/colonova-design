# 비개발자 사용 경험 조사 — 2026-10-10

> 조사만 하고 코드는 고치지 않았다 — 권장만 적는다. 실제 사용자는 개발 지식이 없는 기획자 · 디자이너 ·
> 운영 담당자다. git · 브랜치 · 커밋 · PR 을 모르고, 터미널을 쓰지 않으며, 영어 오류 문장을 보면 그대로
> 멈춘다. 사용자가 아는 말은 제품이 쓰는 말(보관 · 제출 · 반영됨 · 보내기)뿐이다.

## 방법 · 표기

- 문서(README · GUIDE · DEVELOPERS · beta-windows-session — 조사 당시에는 PLAN-FEEDBACK 도 함께
  읽었다)가 약속한 경험과 화면 · 코드를 대조했다. 사용자의 첫 순간부터 순서대로 — 설치 · 첫 실행 →
  온보딩 → 첫 요청 → 기다림 → 결과 확인 → 보관 · 되돌리기 → 제출 → 실패 — 따라갔고, 실패 경로는 데몬 ·
  데스크톱에서 사용자 문장까지 가로로 전수했다.
- 화면 문장의 기준은 `packages/web/src/next/labels.ts` 의 `L`(개발자용 폴드는 `DEV`), OS 알림은
  `packages/desktop/src/copy.ts` 다.
- **[추정]** 이 붙지 않은 주장은 전부 파일 · 문서에서 직접 읽은 것이고, 줄 번호는 2026-10-10 기준이다.
  추론에 의존하는 주장만 [추정] 으로 표시한다. 조사에 쓴 하위 탐색 중 코드에서 다시 읽어 **기각한 주장
  셋**은 부록 A 에 남긴다.
- 판정 기준 — 심각도: 막힘(진행 불가) / 불편(허들이 됨) / 사소. 종류: 기존 수정 / 신규 추가 / 문구·안내만.

## 발견

### 설치 · 첫 실행 · 온보딩

**F1. mac 첫 실행의 벽은 문서에만 있다** — 불편 / 문구·안내만
- 상황 — 서명 없는 배포라 mac 은 Gatekeeper `그래도 열기`, Windows 는 SmartScreen `추가 정보 → 실행` 을
  통과해야 한다(README 233–241 · `site/index.html:1102–1106`).
- 문제 — 앱이 뜨기 전이라 앱 안에서 도울 수 없는 것은 필연이다. 그러나 앱을 옮긴 뒤에도 회복 길이 없다 —
  README 의 `응용 프로그램` 폴더 안내는 있지만, 첫 실행 이후 앱 안에서 다시 볼 문장은 없다.
- 제안 — 소개 페이지의 단계 그림을 유지하고, 첫 화면(체크리스트) 머리에 "처음 열었을 때 막혔다면 → 설치
  안내" 한 줄을 둔다.

**F2. 업데이트 때마다 키체인 허용이 다시 묻는 것 — 어디에도 설명이 없다** — 불편 / 문구·안내만
- 상황 — 릴리스 CI 는 늘 ad-hoc 서명으로 짓고 공증은 없다(DEVELOPERS 1729–1737). cdhash 가 빌드마다
  바뀌어 "업데이트할 때마다 키체인(Safe Storage) 허용을 다시 묻는다"(같은 줄).
- 문제 — 이 OS 알림은 비개발자에게 외국어다. `거부` 를 누르면 복호화가 실패해 자격 증명이 "없던 것으로"
  취급된다(`safe-storage-store.ts:28–37` — `catch` 에서 null). 연결이 조용히 끊긴 것처럼 보이는데, 화면
  문장은 이 원인을 말하지 않는다. GUIDE · README 어디에도 이 허용을 `허용해 주세요` 라고 쓴 곳이 없다.
- 제안 — 첫 업데이트 직후 한 번, "업데이트했습니다 — 열리는 창에서 허용을 눌러 주세요" 안내를 더한다.
  근본 해결은 정식 서명이지만 비용 문제라 별도 과제다.

**F3. 도구 준비 게이트의 문장이 터미널 명령을 말한다** — 사소 / 문구·안내만
- 상황 — git 이 없으면 "git이 없습니다 — 터미널에서 … 로 설치한 뒤 다시 확인해 주세요"
  (`onboarding.ts:212–225`), mac 의 설치 길은 `xcode-select --install` (:537–571). 화면 문장 자체는
  한국어지만 "터미널에서 실행"은 터미널을 쓰지 않는 사용자에게 행동 불가 문장이다.
- 완화 — Windows 는 MinGit 을 번들하고 mac 릴리스도 git 을 번들한다
  (`.github/workflows/desktop-release.yml:106–107 · 135–136`). 정상 배포에서는 이 길이 거의 안 온다.
- 제안 — 이 길에 닿으면 터미널 대신 "이 화면에서 설치를 눌러 주세요" 로 말하거나, 번들 누락 전용 문장
  ("앱을 다시 설치해 주세요") 으로 갈라낸다.

**F5. "other" 설치 실패 — 영어 마지막 줄이 「IT 담당자에게 보낼 문장」 상자에 들어간다** — 불편 / 기존 수정
- 상황 — 설치 실패는 network / policy / disk / other 네 갈래로 분류된다. other 는
  `설치가 실패했어요 — 다시 시도해 주세요.\n<영어 마지막 줄>` 을 detail 로 보낸다(`agent-install.ts:183–188`).
- 문제 — 화면의 `splitInstallDetail` 은 이유를 묻지 않고 **마지막 줄을 무조건** IT 담당자용 문장으로
  떼어 복사 상자에 넣는다(`FirstRun.tsx:592–605` · 렌더 :355–383). 주석은 "policy 가 아니면 상자는
  없다" 고 약속하는데 코드는 그 약속을 지키지 않는다 — 사용자는 영어를 `문장 복사` 로 복사해 IT 에게
  보내게 된다. 원인은 선로에 이유가 없는 것이다 — `onboarding.install.done` 은 `detail` 만 싣는다
  (`protocol/src/messages.ts:924–929`).
- 제안 — `reason` 필드를 선로에 더하고(policy 여부를 화면이 안다), policy 일 때만 IT 상자를 세우고 other 의
  영어 줄은 `자세히` 접힘으로 내린다.

**F6. 요금제 요구 안내 — 충실하다(확인)** — 그대로 둘 것
- README · GUIDE · 첫 화면 카드가 로그인 전부터 "AI 계정은 유료 요금제여야 해요 — … Pro · Max · Team ·
  Enterprise …" 를 말하고, 알려진 쓸 수 없는 요금제는 첫 요청 전에 막는다(`protocol/src/plan.ts:18` —
  `UNUSABLE_PLANS`, 지금 `free` 하나). 다만 무료 요금제가 `free` 로 읽히는지는 실측 전이라
  DEVELOPERS 1188–1195 가 스스로 [추정] 이라 적어 둔다 — 베타에서 확인할 일이다. 유료 계정 자체는 제품의
  진입 조건이라 추가 기능으로 풀 일이 아니며, 안내 품질은 현재 기준이 좋다.

### 초대 파일 · 프로젝트 준비

**F7. 초대 파일 오류 문장 — 잘 되어 있다(확인)** — 그대로 둘 것
- 읽기 실패 갈래(not-invite · sealed · unreadable · version · token · content · file)마다 해요체 문장이
  있고(labels 1255–1265), 날것은 `자세히` 접힘으로 내려간다. "프로젝트는 하나도 바뀌지 않았어요" 같은
  무손상 보증이 먼저 온다. 더블클릭으로 여는 길이 실패해도 같은 오류 카드에 닿는다(`invite-open.ts`).

**F8. 클론 · 포트 충돌 등 준비 실패가 한 문장으로 수렴한다** — 불편 / 기존 수정
- 상황 — 준비(내려받기 · 설치 · 미리보기 켜기) 실패는 `화면을 띄우지 못했어요` + `다시 시도` +
  `담당자에게 보낼 내용 복사` 로 수렴한다(labels 668–672, `PrepareCard.tsx`).
- 문제 — **[추정]** 비공개 레포 · 권한 문제처럼 "다시 시도" 로 풀리지 않는 갈래도 같은 문장을 얻는다.
  진단 복사 글은 개인정보를 잘 가리지만(종류 · 숫자 · 버전만), 실패 종류를 사람 말로 담지 않아 담당자가
  화면만 보고 원인을 알기 어렵다.
- 제안 — 준비의 세 단계는 이미 화면에 있으므로, 실패한 **단계 이름** 을 실패 문장에 싣는 것만으로 담당자
  전달력이 올라간다.

### 첫 요청 · 기다림

**F9. 재시도 5번(총 약 21분) 동안 "몇 번째 · 다음 시각" 이 진행 줄에 안 보인다** — 불편 / 문구·안내만
- 상황 — 일시 실패는 4초 → 16초 → 1분 → 5분 → 15분 사다리를 탄다(`budgets.ts:44–50`). 진행 줄은
  `조금씩 기다리며 다섯 번 다시 묻는 중 · n/5` 만 있고 다음 시각이 없다. 같은 화면의 사용량 팝은
  `10월 3일(토) 03:00에 다시 차요` 처럼 정확한 시각을 말한다.
- 문제 — 15분 계단에서 사용자는 15분간 `n/5` 만 본다. GUIDE 의 「스스로 다시 시도」 도 총 대기 시간을
  말하지 않는다.
- 제안 — `retrying` 문장에 다음 시각을 붙인다(사용량 팝과 같은 문법 재사용).

**F10. AI 가 물어봐요 — 답하지 않으면 그 대화는 멈춘 채다** — 불편 / 신규 추가
- 상황 — 질문 · 허용 요청은 대기로 쌓이고 만료 처리가 없다(데몬 전역에서 질문 시간 제한 흔적 0건 — 검색
  확인). 홈의 `답을 기다려요` 배지와 OS 알림만 남는다.
- 문제 — "기다린 지 얼마나 됐는지" 가 안 보인다. 개발자 확인 대기에는 `· N일째` 가 있는데 질문 대기에는 없다.
- 제안 — 질문 카드에 경과 시간(`· 2시간째`) 을 붙인다.

**F11. 예상 시간 안내는 첫 요청의 한 줄이 전부다** — 사소 / 문구·안내만
- 상황 — 첫 턴 힌트("처음은 몇 분 걸려요") 는 첫 턴에 60초 뒤에만 선다
  (`making.ts:16–17` `FIRST_TURN_HINT_MS = 60_000`). 10분이 넘어도 화면은 같다. 멈추기 단추는 있다
  (`Composer.tsx:780–788`).
- 제안 — 흐른 시간이 문턱(예: 10분)을 넘으면 한 줄 덧말("오래 걸리는 작업이에요 — 멈추기로 언제든 멈출 수
  있어요") 을 세운다.

**F12. 실패의 정직함 — 잘 되어 있다(확인)** — 그대로 둘 것
- 계정류는 "다섯 번 물었다" 는 거짓 없이 곧바로 계정 문장으로 끝내고(`turn-retry.ts`), 재시도 중에는
  실패가 아니라 `지금은 스스로 다시 묻는 중이에요` 로 말한다. `다시 시도` 는 핀 · 그림 · 파일까지 원본
  그대로 되살리고, 되살릴 수 없으면 `첨부는 다시 붙여 주세요` 로 말해 AI 의 어림짐작을 막는다
  (`retry-send.ts`).

### 결과 확인 · 미리보기 · 되돌리기

**F13. 로그인이 필요한 화면 — 사용자에게 보이는 문장이 하나도 없다** — 불편(큰 허들) / 신규 추가
- 상황 — 검증 창은 사용자의 로그인 세션을 쓰지 않아 로그인이 필요한 화면은 로그인 화면으로 튕긴다. 판정
  (`login-wall.ts`) 은 AI 에게 `loginWall` 을 실어 주지만 **사용자 문장은 일부러 만들지 않았다** —
  DEVELOPERS 749–752 가 "결과 카드에 … 따로 세우는 것도 하지 않았다(사용자 문장 결정이 필요하다)" 고
  적어 둔다.
- 문제 — ① 사용자는 갑자기 로그인 화면만 보고 무슨 일인지 모른다. ② 넘기기 화면 캡처 · 수정 전·후 사진도
  같은 창이라 **로그인 화면 사진이 그대로 찍혀** 비교와 제출에 실린다(같은 문서 750–751). 비개발자는
  "AI 가 로그인 화면을 만들었다" 고 오해할 수 있다.
- 제안 — 판정이 이미 있으므로 비용은 작다. (a) 결과 카드에 "로그인이 필요한 화면은 열어 보지 못했어요"
  한 줄, (b) 전·후 사진 위에 "로그인 화면이에요" 표시. 문장 선택(로그인해도 되는지 어디까지 안내할지)은
  제품 판단이 필요해 이번 조사에서 정하지 않았다.

**F14. 말로만 설명한 요청 — 화면에 아무 흔적이 없다** — 불편 / 신규 추가
- 상황 — `고친 화면` 카드는 실제로 화면이 바뀐 턴에만 선다(`request-results.ts:76–78`, `screens.length > 0`
  필터). "이게 뭐야?" 같은 설명 요청이나 화면 밖 파일(설정 · 데이터)만 바뀐 요청은 카드도 확인 줄도 없이
  정산 줄만 남는다.
- 문제 — "내 부탁이 아무것도 안 바뀌었나?" 로 읽힌다. `화면에 드러나지 않은 변경` 은 제출 확인 창에서만
  나온다.
- 제안 — 화면은 안 바뀌었지만 파일은 바뀐 턴의 답 아래에 "화면 대신 설정을 고쳤어요" 한 줄(카드 없이)을
  세운다.

**F16. 자동 고침 · 보관 실패의 조용함 — 대체로 잘 설계됐다(확인, 예외 하나)** — 예외만 기존 수정
- 미리보기 오류는 오류 키당 자동 고침 2회 · 보류 6개 상한이라 무한 반복이 없고(`use-preview-errors.ts:8–13`),
  사용자에게 "고쳐 달라" 를 묻는 화면이 하나도 없다. 보관 실패도 조용한 재시도 → 자동 대화 정리 → 치워 둔
  작업 자동 복구까지 사용자 몰래 끝낸다.
- 예외 — **자동 보관 정리가 계속 실패할 때** 사용자에게 서는 문장이 GUIDE 문제 문장 표(629–652) 와 labels
  에 없다. 상한을 넘으면 문제 문장 한 줄(예: "작업은 이 컴퓨터에 남아 있어요 — 보관이 늦어지고 있어요") 을
  표에 추가한다.

### 제출 · 코멘트 · 반영

**F17. 제출 잠김 이유 · 실패 분류 — 우수하다(확인)** — 그대로 둘 것
- auth(새 초대 파일) / permission(개발자가 코드의 권한 수정) / limit(시간이 푼다) / network(연결되면 자동)
  을 가려서 말하고(`submit-state.ts`, `submit-copy.ts`), "받을 개발자를 확인하지 **못했어요**" 처럼 아는
  것만 말한다. permission 에서 "새 초대 파일이 해결이 아니다" 를 말하지 않는 것도 정확하다.

**F18. 「담당자에게 보낼 내용 복사」에 영어 분류 토큰이 섞인다** — 사소 / 기존 수정
- 상황 — 복사 글은 `${본문}\n${lastError}` 를 이어 붙인다(`status/parts.tsx:143–149`). `lastError` 는
  `auth` · `other` 같은 영어 분류 토큰이다.
- 문제 — 담당자에게 붙여 넣는 글에 낱말만 붙는다 — 행동 지시가 없어 결국 설정 `개발자용` 의 진단 덩어리를
  따로 복사해야 한다. 두 복사 길(가벼운 복사 · 진단 덩어리) 의 차이를 GUIDE 가 설명하지도 않는다.
- 제안 — 복사 텍스트에서 영어 토큰을 한국어로 바꾸거나 빼고, 문제 줄 복사에 진단 요약(종류 · 숫자만인 기존
  원칙 유지) 을 함께 붙인다.

**F19. 개발자 코멘트는 동의 없이 AI 가 반영한다 — 문서화된 설계(그대로 둘 것)**
- 동의 버튼이 없는 것은 GUIDE §9 의 설계다. 반영 차례는 작업 기록에 `의견을 반영했어요` 로 남고 되돌릴 수
  있으며, 코멘트마다 "무엇을 바꿨는지, 바꾸지 않았다면 왜인지" 를 요구하는 기준 줄이 있다
  (`protocol/src/turn-marker.ts:349–379`). 승인 버튼 추가는 제안하지 않는다. 남는 갭은 "질문 코멘트에도
  화면이 바뀔 수 있다" 는 GUIDE §9 의 한 줄 안내뿐이다.

### 도움 · 회복 길

**F25. 기능 제안이 GitHub 계정을 요구할 수 있다** — 불편 / 신규 추가(또는 문구)
- 상황 — 접수는 기계 전체 토큰(초대 파일의 연결 코드) 으로 RELEASES_REPO 에 이슈를 만든다
  (`daemon/src/feedback.ts:74–87`). 토큰이 없거나 401 · 403 · 404 면 **브라우저 마무리** 로 가고, 화면은
  "아직 접수되지 않았어요. **GitHub 로그인을 다시 하거나** …" 을 보여 준다(labels 1509–1510).
- 문제 — 초대 연결 코드는 보통 팀 프로젝트 레포에만 권한이 있다. 다른 레포에 이슈를 만들 권한이 없으면
  브라우저 길에 떨어지고, GitHub 계정 없는 비개발자는 여기서 끝난다 — **[추정]** (GitHub 토큰 권한 동작에
  근거한 추론. 이 한계는 조사 당시 PLAN-FEEDBACK — 뒤의 문서 정리에서 삭제된 문서다 — 가 스스로
  인정했다: "별도 계정 없이 모든 사용자에게 확실한 접수를 보장하려면 제작팀의 접수 서버가 필요하며 이번
  구현에는 포함하지 않는다"). 또한 "막힘 · 버그 보고는
  게시판에 올리지 말 것" 고지(`report.privateNote`, labels 1161) 가 피드백 창에는 없고 설정 `개발자용` 에만
  있다.
- 제안 — 단기: 피드백 창의 공개 고지 아래에 `privateNote` 한 줄을 더한다. 장기: 접수 전용 서버. 기능 제안은
  부가 기능이라 우선순위는 낮다.

**F26. OS 알림에 영어 오류 원문이 실린다** — 사소 / 기존 수정
- `업데이트를 준비하지 못했어요 — ${error}` 같은 OS 알림 본문에 `error.message` 가 그대로 들어간다
  (`desktop/src/copy.ts:137–140`, `app-updates.ts:222–223 · 303–304`). `(HTTP ${status})` · `(종료 코드
  ${code})` 도 같은 파일에 있다(:151 · :177).
- 제안 — OS 알림은 한국어 고지만, 원문은 앱 안 설정 → 업데이트의 `자세히` 로.

## 그대로 둘 것 — 잘 된 점

1. **문장 단일 원천 + 시험 삼중 구조.** 사용자 문장은 labels `L` 한 곳(데스크톱은 copy.ts) 이고,
   `next-labels`(금칙어 · 죽은 칸 검사) · `vocab-sweep`(src 전수 · 면제 사유 명시) · `notice-voice`(데몬
   문장) 시험이 기계로 지킨다. 이번에 찾은 어휘 문제는 전부 "시험 목록이 짧아서" 생긴 것이지 "시험 구조가
   나빠서" 가 아니다 — 목록만 늘리면 된다.
2. **날것 접기 패턴의 일관성.** 초대 오류 · 설정 실패 · 크래시 화면이 모두 "사람 말 먼저 + 날것은
   `자세히`" 로 통일돼 있다. 새 실패 문장은 이 패턴을 따르면 된다 — F5 · F26 의 제안이 전부 이 패턴
   재사용인 이유다.
3. **진단 복사의 개인정보 방어.** "종류 · 숫자 · 버전만" + 이메일 · 경로 · 토큰 마스킹(`maskSecretShapes`
   공유 사전) + 독이 든 입력으로 시험까지. 이 원칙은 함부로 늘리지 말 것 — "도움이 되려고" 파일 경로를
   넣고 싶은 유혹이 반드시 온다.
4. **실패의 정직함.** "받을 개발자를 확인하지 **못했어요**"(없다고 말하지 않음), "네트워크 막힘은 담당자
   몫이 아니다", 계정류는 재시도 없이 곧바로 계정 문장 — 거짓 희망을 팔지 않는 이 자세는 그대로 둘 것.
5. **되돌리기 안전망.** "되돌린 것도 기록에 남고 다시 되돌릴 수 있어요" + 되돌리는 동안 잠김 이유를 그
   자리에 말함 + `방금 한 것 되돌리기` 의 엄격한 조건(`undo-last.ts` — 기록 맨 위일 때만) — 비개발자의
   가장 무서운 동작을 지켜 주는 문장이다.
6. **코멘트 자동 반영 설계(GUIDE §9).** 동의 버튼을 추가하자는 제안을 하지 않는다 — 반영 차례가 기록에 남고
   되돌릴 수 있으며, 코멘트마다 반영 · 미반영 이유를 요구하는 기준 줄이 있다(F19).
7. **보관 실패의 조용함.** 조용한 재시도 → 자동 대화 정리 → 치워 둔 작업 자동 복구까지 사용자 몰래 끝낸다.
   사용자 문장은 최후의 수단이다(F16 의 예외 하나만 문장이 필요하다).
8. **홈 · 시작점 칩 · 첫 준비 알림.** 칩이 쓰던 입력을 덮지 않고, 준비가 끝나는 순간을 "‘이름’ 서비스가 내
   컴퓨터에서 떴어요" 로 한 번만 알리는 흐름 — 첫 5분 설계의 뼈대로 그대로 둘 것.

## 부록 A — 조사 과정에서 기각한 주장

하위 탐색이 보고했으나 코드에서 다시 읽어 **기각**한 주장이다. 본문 어디에도 반영하지 않았다.

1. **"AI 전송 실패 notice 가 영어 원문을 화면 첫 줄에 보인다"** — 데몬은 원문을 빈 줄 뒤에 붙이고
   (`daemon/src/session.ts:1599–1601`), 웹 Thread 는 **빈 줄 앞의 한국어 고지만 잘라** 보인다
   (`chat/Thread.tsx:652–655`). 영어 꼬리는 새 UI 에서 보이지 않는다. 실제 노출은 codex 드라이버의 한국어
   접두 없는 원문 notice(`codex/session.ts:1076`) 와 F5 · F26 뿐이다.
2. **"github 게이트 경고가 FirstRun 에 첫 줄로 노출된다"** — FirstRun 은 github 단계를 아예 그리지 않는다
   (`FirstRun.tsx:61–64` 주석). github 게이트 경고(`onboarding.ts:321–339`) 는 현재 UI 어디에도 렌더되지
   않는다. 오히려 **"연결 코드가 이 레포에 닿지 않는다" 는 사전 안내가 사용자에게 안 보인다** 는 별개
   문제가 있다 — 첫 제출에서 처음 알게 된다(사전 점검은 소개 페이지 쪽에서만 한다).
3. **"모델 힌트 룩업 실패 시 영어가 노출된다"** — `modelHint` 는 사전에 없으면 null 을 돌려 힌트를 아예 안
   그린다(`chat/ModelChip.tsx:34–37`). 영어 노출이 아니다.

### 2026-10-20 — 자동 촬영과 종료 후 검사 축소

사용자 요청(불필요한 이미지 촬영 · 검증과 내장 MCP 절차 축소)으로 화면 확인 의무와 종료 후 자동 게이트를 제거했다. 전후 · 소개 · 제출 사진은 자동 촬영하지 않는다. 사진 없는 결과 카드는 화면 열기와 추가 수정으로 이어진다. 필요한 확인은 작업 중 선택하고, 과거 사진과 확인 기록은 계속 읽는다.

### 2026-10-20 — 보내기 앞의 준비 축소

사용자 제보(실제 기다림보다 짧은 완료 시간)와 개선 요청으로 보내기 앞의 최신화 · 핀 코드 검색 · 파일 내용 비교 · 공급자 대화록 개수 조회를 없앴다. 코드 탐색은 AI가 맡는다. 이미 진행 중인 보관의 순서만 지키고, 편집 후보와 미보관 파일은 답변 뒤 확인한다. 완료 시간은 보내기를 누른 때부터 잰다. 요청별 파일 차분의 정밀 판정은 줄이며, 실기 속도는 베타 7-C에서 별도로 잰다.

### 2026-10-20 — 연결 레포가 개발 규칙을 소유

사용자 요청으로 내장 MCP와 앱 공통 개발 정책을 제거했다. 개발 방법·검사는 연결 레포의 지침·스킬·설정을 따른다. 앱은 실행과 보관·푸시·제출을 맡고, 미리보기·핀·첨부는 사용자 요청의 문맥으로 전달한다. 새 작업은 요청 단위로 함께 보관하고 제출은 화면 버튼으로 한다.
